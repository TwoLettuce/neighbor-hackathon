# Neighbor

Neighbor finds upcoming events where job seekers can build useful professional relationships. It ingests events ahead of time, normalizes and classifies them, stores them in PostGIS, then ranks local and interactive virtual events by career fit and networking potential.

## Stack

- Next.js 16, React, TypeScript, Tailwind CSS
- Django 5, Django REST Framework, GeoDjango
- PostgreSQL 16 + PostGIS
- pytest and pytest-django

## Local setup

Prerequisites: Python 3.12+, Node 20.19+ or 22.13+, Docker Desktop, and GeoDjango native libraries. On macOS install the latter with `brew install gdal geos`.

```bash
cp .env.example .env
docker compose up -d db

python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
python backend/manage.py migrate
python backend/manage.py seed_events
python backend/manage.py runserver
```

In another terminal:

```bash
cd frontend
npm install
npm run dev
```

Open <http://localhost:3000>. Search for `Software Engineer`, `Provo, UT`, and `50 miles`. Django Admin is at <http://localhost:8000/admin/> and browsable OpenAPI documentation is at <http://localhost:8000/api/docs/>.

## Ingestion

The default credential-free command refreshes 24 realistic rolling Utah fixtures and is idempotent:

```bash
python backend/manage.py ingest_events
```

A real public iCal feed can be imported with:

```bash
python backend/manage.py ingest_events --provider ical --feed-url https://example.org/events.ics
```

Only trusted, operator-configured feed URLs should be used. Meetup, Eventbrite, Luma, and Handshake commands are explicit stubs because their supported APIs do not provide unrestricted global public discovery. See `docs/providers/` for current capabilities and legitimate integration paths.

## Verification

```bash
pytest backend/tests
ruff check backend
cd frontend
npm run lint
npm run typecheck
npm run build
```

The integration tests require the PostGIS service. Ranking, classification, deduplication, normalization, ingestion idempotency, API behavior, and geographic radius filtering are covered.

## Project layout

- `backend/events/providers/`: provider contracts and adapters
- `backend/events/ingestion/`: normalization and persistence pipeline
- `backend/events/classifiers/`: rule-based and optional structured-LLM interfaces
- `backend/events/deduplication/`: deterministic duplicate scoring
- `backend/events/ranking/`: explainable ranking components
- `backend/events/services/`: taxonomy, geocoding, and search orchestration
- `frontend/`: search and ranked-results UI
- `docs/`: architecture, ranking, and provider constraints

## Current limitations

Development geocoding recognizes Provo, Orem, Lehi, Draper, South Jordan, and Salt Lake City. iCal location strings are not yet geocoded automatically. There is no user authentication or personalization. Seed source URLs intentionally use `example.com`, and provider stubs require approved partner access before implementation.

## Hackathon deployment

The production topology is a static frontend on GitHub Pages, a Docker-based
Django service on Render, and a Neon PostgreSQL database with PostGIS. Cloud
credentials and connection strings must only be entered in the relevant cloud
dashboard; never commit them.

### Neon

1. Create a free Neon PostgreSQL project.
2. Copy its PostgreSQL connection string, including `sslmode=require`. Use the
   direct connection string for initial migrations; the pooled URL can be used
   by the running service after initialization.
3. The first Django migration runs `CREATE EXTENSION IF NOT EXISTS postgis`
   before creating spatial columns. If extension creation is restricted, open
   Neon's SQL editor and run:

   ```sql
   CREATE EXTENSION IF NOT EXISTS postgis;
   SELECT PostGIS_Version();
   ```

4. Store the connection string as Render's `DATABASE_URL`; do not add it to
   `.env` in source control.

### Render

The included `render.yaml` and `backend/Dockerfile` deploy the backend with the
native GDAL/GEOS libraries GeoDjango requires. The container collects static
files during its build, serves them with WhiteNoise, runs migrations at startup,
and starts Gunicorn. Running migrations on startup is appropriate for this
single-instance hackathon service and avoids relying on a paid pre-deploy job.
It does not seed or replace data.

1. In Render, create a Blueprint from this repository and select `render.yaml`.
   Alternatively, create a free Docker Web Service with repository root as the
   root directory, `backend/Dockerfile` as the Dockerfile, and `/api/health/` as
   the health-check path.
2. Configure these Render environment variables:
   - `DATABASE_URL`: the secret Neon connection string.
   - `DJANGO_SECRET_KEY`: generated by the Blueprint or a strong random secret.
   - `DJANGO_DEBUG`: `false`.
   - `DJANGO_ALLOWED_HOSTS`: the hostname only, such as
     `<render-service>.onrender.com`.
   - `CORS_ALLOWED_ORIGINS`: the GitHub Pages origin, such as
     `https://<github-user>.github.io`. Do not include the repository path or a
     trailing slash.
3. Deploy and confirm
   `https://<render-service>.onrender.com/api/health/` returns
   `{"status":"ok"`.
4. Initialize demo data once. Use Render's service shell, if available:

   ```bash
   python manage.py seed_events
   ```

   If a shell is unavailable on the free plan, run the command locally against
   Neon using the same URL:

   ```bash
   DATABASE_URL='<neon-url-with-sslmode-require>' \
   DJANGO_DEBUG=true \
   python backend/manage.py seed_events
   ```

   `python backend/manage.py ingest_events` remains available for later
   idempotent refreshes.

Render free services can spin down while idle. The first API request after an
idle period may take roughly a minute; the frontend will remain available while
the backend wakes.

### GitHub Pages

The workflow in `.github/workflows/deploy-pages.yml` creates a Next.js static
export, derives the project-site base path from the repository name, uploads
`frontend/out`, and deploys it with the official Pages actions.

1. In GitHub, open **Settings → Pages** and select **GitHub Actions** as the
   source.
2. Open **Settings → Secrets and variables → Actions → Variables** and create
   `NEXT_PUBLIC_API_BASE_URL` with the Render HTTPS origin, for example
   `https://<render-service>.onrender.com`. It is intentionally a repository
   variable, not a secret, because browser code must know the public API URL.
3. Push to `main` or manually run **Deploy frontend to GitHub Pages**.
4. The project site will be available at
   `https://<github-user>.github.io/<repository>/`. Repositories named
   `<github-user>.github.io` are automatically built without a base path.

For a custom local frontend API URL, create `frontend/.env.local`:

```dotenv
NEXT_PUBLIC_API_BASE_URL=http://localhost:8000
```

Without that file, local development uses the same localhost default.

### Production environment reference

Configure on Render:

- `DATABASE_URL` — secret Neon PostgreSQL URL with SSL required.
- `DJANGO_SECRET_KEY` — secret random value.
- `DJANGO_DEBUG` — exactly `false`.
- `DJANGO_ALLOWED_HOSTS` — comma-separated hostnames without schemes.
- `CORS_ALLOWED_ORIGINS` — comma-separated browser origins with schemes.

Configure as a GitHub Actions repository variable:

- `NEXT_PUBLIC_API_BASE_URL` — public Render HTTPS origin.

The workflow derives `PAGES_BASE_PATH`; it does not need to be configured
manually. Local `POSTGRES_*` values and Docker Compose continue to work when
`DATABASE_URL` is absent.
